## `importTransactions` with `dryRun: true`: `updatedPreview` entry shapes

`reconcileTransactions` (L121652) iterates `transactionsStep3`. With `isPreview` nothing is written, but `added`/`updated` id arrays are still populated (added ids are fresh `v4()` that are never persisted).

| Case | Pushed to `updatedPreview` | Counted in |
|---|---|---|
| Matched row, `match.reconciled` truthy | `{ transaction: trans, ignored: true }` | nothing |
| Matched row, fields would change | `{ transaction: trans, existing }` where `existing` = the matched DB row with `cleared` boolean, `date` as `YYYY-MM-DD`, `payee_name` set, `amount` in **units** (`integerToAmount`) | `updated` |
| Matched row, nothing changes | `{ transaction: trans, ignored: true }` | nothing |
| `trans.tombstone` (deleted row seen again) and `isPreview` | `{ transaction: trans, existing: false, tombstone: true }` | nothing |
| **No match (row will be added)** | **nothing is pushed** | `added` (ids) |
| `trans.skipTransaction` | nothing | nothing |

Consequences for the tool:
- Rows to be added are not in `updatedPreview`; derive them as the input rows that appear in neither `updatedPreview[].transaction` nor as ignored (compare by `imported_id`; the id list `added` only gives count/length in preview). Safest: use `added.length` for the count and match input rows against `updatedPreview` by `transaction.imported_id` to list the rest as "new".
- `trans` in each entry is the post-rules, post-normalization row (payee name normalized, `payee` resolved), not the raw input.
- An `existing` with `reconciled` true is reported as `ignored`, never as an update.
- Matches found by the fuzzy path look identical to id matches; tell them apart by comparing `existing.imported_id` to `transaction.imported_id` (fuzzy matches have no `imported_id` on the existing row).

## `applyTemplate` / `overwriteTemplate` return values (`processTemplate`, L129104 region)

| Situation | Return value |
|---|---|
| Budgets written | `{ type: "message", message: "templates-applied", count: <number of categories budgeted> }` |
| Nothing to do (no contexts, no errors) | `{ type: "message", message: "templates-up-to-date" }` (orphan goals are cleared as a side effect) |
| Template parse/evaluation errors (any category) | `{ sticky: true, message: "template-errors", pre: "<Category>: <message>\n\n<Category>: ..." }`. **No budget is written** in this case. Note there is no `type` field. |
| (`budget/check-templates`, not used by the tools but useful) | `{ sticky: true, message: "template-errors", pre }` or `{ type: "message", message: "templates-check-passed" }` |

- Template lines that failed to parse are stored as `{type: "error", ...}` entries (by `storeNoteTemplates`) and `checkTemplateNotes` reports them; during `computeTemplates` a per-category exception becomes an `errors` entry `"<name>: <e.message>"`.
- The review-focus item mentions `{ type: 'error' }`: that shape comes from stored template entries, while the handler's return for errors is the `sticky` form above. Tool code should treat both `result.sticky` / `message === "template-errors"` and `result.type === "error"` as errors.
- Without `force` (apply), categories whose current `budgeted` is not 0 are skipped; `overwrite` (`force = true`) recomputes all categories with templates. Both call `storeNoteTemplates()` first, which rewrites `goal_def` for every non-`ui` category from its notes (a side effect even when nothing is budgeted).
